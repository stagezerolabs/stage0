# NFT marketplace on RISE: implementation research

Research date: 2026-09-24. This note concerns secondary trading of NFTs on Stage0, distinct from minting on the launchpad and trading `.rise` names. Sources are standards, first-party protocol documentation, and the current repository.

## Standards and asset handling

- ERC-721 identifies an asset by `(chain, contract address, tokenId)`. The owner, a token-approved address, or an approved operator may transfer it. `approve` scopes authorization to one token; `setApprovalForAll` authorizes an operator for the owner's entire collection. A marketplace should show this scope before prompting for approval, check `ownerOf` and current approval again at purchase, and use `safeTransferFrom` for receipt by a contract. [ERC-721](https://eips.ethereum.org/EIPS/eip-721).
- ERC-1155 uses `(chain, contract address, tokenId, quantity)`. It exposes `balanceOf`, `setApprovalForAll`, safe single/batch transfers, and `TransferSingle`/`TransferBatch` events. There is no standard token-specific approval. Quantities and partial fills add meaningful contract, indexer, and UI complexity. [ERC-1155](https://eips.ethereum.org/EIPS/eip-1155).
- Detect ERC-721 and ERC-1155 with ERC-165 before using an unfamiliar collection, and reject unsupported or ambiguous implementations. Metadata can be remote or mutable; treat names, images, attributes, and links as untrusted presentation data, while ownership and sale validity come from chain state. [ERC-165](https://eips.ethereum.org/EIPS/eip-165), [ERC-721 metadata](https://eips.ethereum.org/EIPS/eip-721), [ERC-1155 metadata](https://eips.ethereum.org/EIPS/eip-1155).
- ERC-2981 `royaltyInfo(tokenId, salePrice)` returns a recipient and amount in the sale currency. It supplies royalty information, not enforcement; a marketplace decides whether to pay. If supported, calculate and display seller proceeds and royalty at the current sale price, then enforce the chosen payout policy in the settlement contract. [ERC-2981](https://eips.ethereum.org/EIPS/eip-2981).

## Trading architecture

| Model | How it works | Consequences |
| --- | --- | --- |
| On-chain escrow, fixed price | Seller approves and deposits an NFT into a marketplace contract; buyer pays and receives it atomically; seller can cancel and withdraw. | Smallest honest trading MVP and simple event indexing. Seller gives up custody while listed and pays a listing transaction. Need explicit rescue/recovery rules and receiver interfaces. |
| Noncustodial signed orders | Seller grants operator approval and signs a typed order; buyer presents it to a settlement contract, which checks signature, nonce, time, ownership, approval, and price before transfer. | Familiar OpenSea-like listing UX without custody or listing gas. Requires an off-chain order service, cancellation/nonce handling, EOA and contract-wallet signatures, and careful replay protection. Approval may cover a whole collection. |
| Seaport | Orders specify offers, consideration, zone, conduit, time, counter, and optional criteria; fulfillment can match or partially fill orders. | Mature protocol with broad capabilities, but integration needs verified deployment and compatibility on RISE, plus an order service and substantial validation. This repo has no proven RISE Seaport deployment. |

OpenSea's first-party documentation confirms that Seaport uses offer/consideration orders and a service that listens to and stores events; its detailed protocol docs enumerate order components, signatures, approvals, cancellation, and fulfillment. [OpenSea overview](https://docs.opensea.io/docs/seaport), [Seaport documentation](https://github.com/ProjectOpenSea/seaport/blob/main/docs/SeaportDocumentation.md). A Seaport-style experience is more than a gallery or a wallet `transferFrom` button. Neither a contract deployment nor a real order path should be implied by UI copy before verified.

**Recommended first release:** browse collections and individual tokens, show ownership and metadata, and implement audited fixed-price ERC-721 sales in native ETH through a small escrow contract. Add ERC-1155 quantities, offers, auctions, or noncustodial signatures in later milestones when contract and indexer support exist. This is a scope recommendation, not a claim that escrow is as flexible as Seaport. If the product specifically requires gasless listings, switch the settlement design before implementation to EIP-712 signed orders rather than layering signatures over escrow.

For signed orders, EIP-712's domain should bind `chainId` and `verifyingContract`; a listing also needs asset, seller, payment token/amount, expiry, and nonce/salt to prevent replay or unwanted reuse. The standard itself does **not** provide replay protection; the settlement design must. Smart-contract wallets require ERC-1271 `isValidSignature`, not ECDSA recovery alone. [EIP-712](https://eips.ethereum.org/EIPS/eip-712), [ERC-1271](https://eips.ethereum.org/EIPS/eip-1271). Seaport's own checks include current balance, approval, time, cancellation, signature, and fill status. [Seaport documentation](https://github.com/ProjectOpenSea/seaport/blob/main/docs/SeaportDocumentation.md).

## Security and failure modes

- Settlement must be atomic: verify live owner/balance, approval, active listing, exact price and fee/royalty bounds, then mark it filled or cancelled before external transfers; guard reentrancy and use a payout approach that cannot strand all sales if one recipient rejects ETH. Receiver callbacks can execute arbitrary code. The safe-transfer receiver hooks are specified in [ERC-721](https://eips.ethereum.org/EIPS/eip-721) and [ERC-1155](https://eips.ethereum.org/EIPS/eip-1155); use the current [OpenZeppelin security utilities](https://docs.openzeppelin.com/contracts/5.x/api/utils) where applicable.
- A displayed listing can go stale through sale, cancellation, transfer, approval revocation, expiry, or metadata change. Revalidate against chain state immediately before prompting for payment, simulate the contract call, wait for receipt, then refresh the token and listing. Indexer/API data is for discovery, not authorization. Seaport explicitly checks balance and approval at fulfillment. [Seaport documentation](https://github.com/ProjectOpenSea/seaport/blob/main/docs/SeaportDocumentation.md).
- For signed orders, distinguish an off-chain removal from an on-chain cancellation: removing an order from one API does not revoke a still-valid signature. Expose nonce/counter cancellation and accurately state its gas cost. Seaport supports order cancellation and counter increments. [Seaport documentation](https://github.com/ProjectOpenSea/seaport/blob/main/docs/SeaportDocumentation.md).
- Contract-wallet signatures may become invalid as wallet policy changes; validate them at execution. Do not infer final sale from a pending wallet request or transaction hash. [ERC-1271](https://eips.ethereum.org/EIPS/eip-1271).

## Data and RISE constraints

- The current app defines RISE Mainnet as chain ID `4153`, native ETH, RPC `https://rpc.risechain.com`, and explorer `https://explorer.risechain.com` in [`src/config.ts`](../src/config.ts). RISE describes itself as EVM compatible; standard EVM NFT interfaces are therefore the appropriate baseline, with actual behavior still verified on deployed contracts. [RISE documentation](https://docs.risechain.com/docs).
- Existing [`src/lib/indexer/goldsky.ts`](../src/lib/indexer/goldsky.ts) indexes **launchpad collections**, not token transfers or resale listings. [`src/lib/api/nft.ts`](../src/lib/api/nft.ts) only validates mint metadata. The RNS marketplace address and APIs represent `.rise` names and must not be reused as a general NFT exchange. The repo's [`indexer/goldsky/rns/README.md`](../indexer/goldsky/rns/README.md) says Goldsky's catalog lacked RISE Mainnet at the time and RNS mainnet indexing uses Senna. Recheck provider support before selecting an NFT indexer; do not assume Goldsky mainnet coverage from existing code.
- A real browse page needs collection and token inventory, current owner/balance, listings, sale events, and token metadata. For ERC-721, index `Transfer` (including mint/burn). For ERC-1155, index `TransferSingle` and `TransferBatch`; its standard explicitly allows balances to be reconstructed from events. Index marketplace list/cancel/fill events, make ingestion idempotent by `(chainId, txHash, logIndex)`, handle reorgs, and serve cursor-paginated collection/token/listing queries. [ERC-721](https://eips.ethereum.org/EIPS/eip-721), [ERC-1155](https://eips.ethereum.org/EIPS/eip-1155).
- Discovery has a product trust boundary: decide whether Stage0 supports only its own launchpad collections at first or arbitrary RISE NFT contracts. Arbitrary contracts require collection verification/moderation, spam handling, metadata fetch limits, and unsupported-contract treatment. The standards permit implementations to revert transfers for extra reasons, so a detected interface alone does not guarantee tradability. [ERC-721](https://eips.ethereum.org/EIPS/eip-721).

## Decisions to lock before contract work

1. **Asset scope:** Stage0 launchpad ERC-721 collections only for MVP (recommended), or all RISE ERC-721/1155 contracts.
2. **Trading model:** on-chain escrow fixed-price sales (recommended for a first safe release), or signed noncustodial orders if gasless listing is mandatory.
3. **Economics:** platform fee, whether ERC-2981 royalties are honored, maximum aggregate payout, and who bears those costs. Enforce these in contract, not only in UI.
4. **Operations:** ownership and upgrade authority, pause policy, audit/independent review, deployment target, indexer provider, and launch/rollback procedure. None can be inferred from the frontend repository.

Research does not establish that any general NFT marketplace contract, Seaport deployment, or NFT order API is live on RISE for Stage0. The existing launchpad should remain distinct from this feature.
